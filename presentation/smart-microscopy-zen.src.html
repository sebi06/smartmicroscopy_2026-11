The interface landscape

Data access and instrument control are different interfaces.

  • CZI and its librariesRead image pixels and metadata with tools such as libCZI or pylibCZIrw. A file reader does not move the microscope.
  • Internal OAD and Experiment FeedbackRun inside ZEN. Access internal workflow functions or acquisition-time observables and actions.
  • COM and TCP/IPExpose established scripting routes to external software. COM uses Windows automation; TCP/IP sends scripting commands or starts a macro.
  • C# extensionsAdd application-integrated functionality through the ZEN extension mechanism. This is a different integration model from an external API client.
  • ZEN-APIUses typed services for external monitoring and control, including acquisition, selected hardware functions, and pixels during acquisition.
Important distinction

The TCP/IP scripting interface and the gRPC-based ZEN-API are not the same protocol. A TCP/IP macro command is not a ZEN-API method.

Reference: included interface overview. Exact availability depends on the ZEN edition, version, licensed functionality, and instrument.

Open Application Development

OAD makes ZEN the workflow host.

Open Application Development (OAD)

Record supported operations, edit scripts, and combine acquisition, processing, analysis, saving, and user dialogs.

  • Good fit: ZEN owns the workflow and the required functions exist in its scripting interface.
  • Strength: broad access to ZEN-internal functions, including processing and analysis not all exposed by ZEN-API.
  • Constraint: the supplied scripting environment uses IronPython, not ordinary CPython.
  • Consequence: do not expect to import CPython-native packages such as NumPy or SciPy directly.

External Python, Fiji, or other software can be invoked from a script. That adds a process and data handoff; it does not turn IronPython into CPython.

What OAD is not

It is not a promise that every UI operation is recordable. An unrecorded operation may still have a scripting command. OAD is also not synonymous with the Guided Acquisition module: the script is one way to implement a custom guided workflow.

Basis: included OAD runtime illustration and public ZEN-API README: API and internal scripting.

Adaptive Acquisition Engine

Experiment Feedback changes a running experiment.

PreLoop: prepare once

Import modules, define functions, and initialize variables at the start of the experiment.

Loop: react to change

Evaluate rules when a used observable changes. Read online measurements or hardware state and issue permitted actions.

PostLoop: finish once

Write final results or start follow-up work when acquisition finishes. The feedback script is stored in the experiment.

Make the rule explicit.

  • Stop acquisition after enough objects have been detected.
  • Adjust permitted acquisition parameters in response to sample changes.
  • React to a trigger, stage position, or environmental observable.
  • Log measurements or start an external application.
Not an unconditional polling loop

The Loop script is triggered by changes in observables used by the script. It does not automatically execute forever or once per arbitrary time interval.

Synchronization determines which data your rule can trust.

Do not assume results are ready

Script execution can overlap online analysis and disk writing. This mode does not guarantee their completion first.

Wait for analysis

Select an order in which analysis finishes before the script runs when the rule needs current measurements.

Wait for analysis and disk

Use the order that also completes image writing before starting external software that must read those pixels.

Define the required measurements in the image-analysis setting first. Reload a changed setting in the feedback editor. Synchronization and script cost affect acquisition timing.

ZEN 3.14 tutorial, pages 7-11. The source also distinguishes Free Run from Synchronized execution; select the appropriate execution order in that version's UI.

Overview / detection / detailed acquisition

Guided Acquisition spends detail on selected objects.

The ZEN module: configure the workflow

A dedicated module provides a streamlined UI. Select overview and detail experiments, optional processing, and an image-analysis setting.

  • No scripting knowledge required for the standard workflow.
  • Checks required analysis parameters and supports well-plate workflows.
  • Integrates supported processing steps before detection.
  • A separately offered module; confirm entitlement and instrument support.

Choose how to find objects.

ZEN Guided Acquisition can incorporate machine-learning and deep-learning methods to detect objects in the overview:

  • Semantic Pixel Classifier: classify pixels into target and background classes using trained image features.
  • Semantic DL Models: use neural networks to assign pixels to classes and derive target regions.
  • Instance Segmentation: identify individual objects, including objects that touch.
  • CellPose Model: segment cells or nuclei to generate candidate objects.
  • External DL models: import compatible models into ZEN or integrate external inference and return detected targets.

Available methods depend on the ZEN version, enabled analysis features, and model compatibility. External inference requires a configured integration, such as a scripted handoff; it is not automatically part of the standard module sequence. The Semantic Pixel Classifier is a machine-learning option, not necessarily a deep-learning model.

The OAD script: own the workflow

A macro implements the same pattern inside ZEN. Customize processing, target selection, experiment modification, and external analysis handoffs.

  • Useful when the module's standard sequence does not fit.
  • Requires IronPython and knowledge of the ZEN scripting interface.
  • The published example script is free to use at your own risk; required ZEN capabilities still apply.
  • You maintain the code, coordinate handling, error paths, and recovery.
Other applications use the same selection pattern.

Basis: Guided Acquisition README and tutorials. “Module” and “script” describe the implementation and user experience, not two different biological selection principles.

A concrete event-driven workflow

Find mitosis early, then follow the event.

The biological question sets the acquisition.

A useful recording must include the event's start, not only a bright cell found too late.

  • Screen a broad field at low magnification.
  • Segment candidates and reject unwanted objects.
  • Acquire selected cells with a suitable time-lapse and Z-stack.
  • Track the event and measure anaphase initiation downstream.

Sequential well processing reduces the delay between detection and detail. Classification errors and time spent acquiring each stack still limit useful throughput.

A custom OAD example makes the scheduling logic visible.

ZEN-API deep dive / architecture

Your application owns the workflow. ZEN owns acquisition.

ZEN-API connects an external process to a running ZEN system. It exposes services, not mouse clicks.

ZEN 3.14: ZEN-API documentation (2026.5.1)ZEN-API overview and setup README

Client

Your Python program or other application calls services, analyzes data, and chooses the next action. It can run locally or on another permitted machine.

Gateway

A separate application routes calls to registered providers and handles shared concerns such as access management and aggregated service descriptions.

API provider

A running ZEN ecosystem application hosts an API server and registers its services. The provider implements the microscope-specific operation.

A complementary interface

ZEN-API does not replace OAD or expose every internal ZEN function. It is not a UI-automation interface. Check that the exact operation exists for the running system before designing the workflow.

Basis: public ZEN-API overview, gateway, and glossary. LM means light microscopy; EM means electron microscopy. A shared acquisition concept does not imply identical hardware support.

ZEN-API deep dive / contracts

A typed contract separates the client from ZEN internals.

Protocol Buffers

A .proto file defines services, request and response messages, and fields. It is the contract, not the microscope driver.

gRPC

Remote Procedure Calls use HTTP/2 and Protocol Buffers. Methods can return a response or a stream of responses.

Generated client stubs

A stub makes a remote service callable from your program. Generated messages enforce the API's data structure; they do not supply unsupported server features.

The Python layers have different jobs.

  • zen_api supplies the generated API messages and gRPC client wrappers.
  • zen_api_utils supplies separate, application-side connection and workflow helpers.
  • NumPy, image analysis, AI inference, and visualization are client-side choices, not requirements of the gateway.

Version matching is part of the design.

Package version, service namespace, and server capabilities are separate concerns. Namespaces such as v1 and v1beta coexist in a package.

A method present in a generated package may still be unavailable on an older ZEN server or a different instrument.

Basis: contract-generation overview, utility package documentation, and versioned proto contracts.

ZEN-API deep dive / data during acquisition

PixelStream delivers pixels with acquisition context.

Keep with the pixelsWhy it matters
Experiment ID and frame numberAssociate a response with its experiment and frame; do not identify frames only by arrival time.
Frame positionUse the acquisition indices, such as time, Z, channel, tile, and scene, when organizing the data.
Stage position and scalingRelate image measurements to physical locations. Verify coordinate frames, origins, and units.
Pixel type, full-frame size, and raw bytesDecode the correct type and shape. A byte payload is not already a NumPy image.
Payload start position and sizePlace partial data at the correct offset within the full frame. Do not reshape every response as a complete image.

Get the next frame

The reviewed service offers single-response methods such as GetNextFrame, optionally scoped to an experiment or channel.

Monitor an experiment

MonitorExperiment and MonitorAllExperiments return server streams. Select the intended experiment and channel scope.

Choose assembled or raw data

The monitor requests include enable_raw_data. Raw data can contain partial frames or lines; the non-raw mode assembles full frames.

Engineering guidance: keep the loop responsive.

Separate pixel reception, expensive analysis, and hardware decisions. Bound buffering, record processing lag, and define what happens when analysis is slower than acquisition. Do not claim hard real-time performance from a demo video.

Basis: ExperimentStreamingService, FrameData, and FramePixelData contracts; pixel-stream example. The concurrency guidance is a design recommendation, not an API delivery guarantee.

ZEN-API in an external viewer

napari can watch, start, or store a ZEN acquisition.

Watch an experiment

Start acquisition in ZEN Blue and let napari display incoming frames. Connecting does not start an acquisition. The passive mode does not know the experiment ID in advance; run only one acquisition at a time.

Start the selected setup

Select a prepared experiment, then start it from napari. The plugin reads experiment dimensions from exported XML and filters frames by the returned experiment ID.

Write OME-Zarr directly

The OME-ZARR-only mode uses a dedicated channel and writer rather than the Display pipeline. It can start the experiment or arm the writer before a manual ZEN start.

Display and storage use different paths.

Display mode receives frames through an asynchronous reader, queue, and processor. It can show only the latest frame, but still retains received frames for final scene assembly.

After acquisition, tiles are placed using streamed positions into scene mosaics per channel. A lightweight live preview does not mean acquisition memory use stays constant.

Completion needs more than a finished status.

The repository documents that final pixel payloads can arrive after ZEN reports acquisition complete. A napari-started Display run also waits for its expected unique frame count, with inactivity as a fallback.

The configured writer checks expected coordinates. Missing frames can leave a partial store and an error; inspect acquisition_status.json rather than assuming success.

Preview is not raw quantitative data

The reviewed Display path assumes uint16 input and normalizes each frame for visualization. Do not compare its layer intensities as untouched acquisition values. The configured OME-Zarr writer preserves supported raw GRAY8 or GRAY16 intensities; it does not support color pixel types.

Check the plugin's own compatibility and operating limits.
  • The repository describes an alpha / MVP project, targeting ZEN Blue and its gateway on Windows. The package requires Python 3.12-3.14; this is narrower than the API utility package's support range.
  • Install compatible zen_api and zen_api_utils wheels in the same environment as napari. They are required dependencies, not implied downloads from PyPI.
  • The documented API dependency range is 2026.5.1 through 2026.11.1. Match the gateway and instrument, not only the plugin.
  • The configured CLI and plugin share the direct writer. The older unconfigured CLI mode buffers the acquisition and does not provide the same completeness certification.
  • Linux-to-Windows remote streaming is experimental in this repository. Simulated tests do not establish end-to-end hardware throughput or frame completeness.
  • Stream reception, visualization, and writing are not by themselves a sample-driven feedback controller. The plugin is not documented as automatically running the N2V or semantic models shown in the separate API demos.

Viewing an existing CZI is a separate workflow.

Use a CZI reader to explore existing data. Use the streaming plugin to receive pixels during acquisition. Add a validated decision and control action when the scientific question needs a closed loop.

ZEN-API deep dive / building a smart workflow

External analysis can choose the next experiment.

A complete guided workflow has an explicit handoff.

  1. Acquire an overview from a prepared ZEN experiment and wait for the required completion or data readiness.
  2. Analyze in the client with the appropriate Python libraries or another analysis service.
  3. Validate targets and convert image results into calibrated physical coordinates.
  4. Clone a detail recipe and update the supported regions or positions.
  5. Acquire each target and retain image outputs, target information, and errors.

What does the supplied example actually do?

The Python guided-acquisition example loads and clones experiments, clears tile regions, creates a rectangle, polygon, or ellipse, and runs a detailed acquisition.

Its tile-region calls document physical dimensions in meters. Do not pass segmentation pixel coordinates directly to stage or tile-region APIs.

The example also imports a legacy TCP/IP helper. Treat it as a mixed-interface example; do not assume every supporting operation is a pure ZEN-API call.

One external workflow is not another ZEN core job.

Client-side orchestration

The external program sequences wells, focus, acquisition, file readiness, and analysis. The supplied CD7 example keeps hardware operations sequential while background analysis works on previous CZI files.

Use this when Python must own the complete process or coordinate other systems.

ZEN core workflow services

The API can run ZEN core jobs and modify supported workflow parameters. Consult the versioned API documentation for available services.

A ZEN core job and an acquisition experiment are distinct concepts. Verify available workflow services for that edition.

Delegate the correct-sized block to ZEN.

Avoid replacing a stable experiment with many low-level hardware calls when one supported acquisition block will do. More external flexibility can add coordination and processing overhead.

Close the loop deliberately

Analysis, denoising, or a dashboard alone is monitoring. A smart feedback workflow also has an explicit rule, a supported control action, and a checked result.

Basis: repository control examples and public OAD Python workflows; included workflow-block illustration. Sample loading and carrier navigation are instrument-specific, not generic promises for every ZEN installation.
